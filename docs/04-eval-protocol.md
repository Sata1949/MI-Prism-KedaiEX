# 评测协议

> 目的：把"更强"变成一个可执行、可复现、可证伪的判定。
> 本文定义：测什么、怎么测、和谁比、什么算失败。

---

## 1. 三层指标

| 层 | 指标 | 门槛 | 谁能测 |
|---|---|---|---|
| 预算层 | 显存 / 内存 / 解码速度 | 见 §1.1 | `tools/eval_gate.py`，任何时候 |
| 能力层 | 四类任务分数 | 见 §3 | 需要真实权重 |
| 体验层 | 首 token 延迟、长文稳定性 | 见 §4 | 需要真实权重 + 交互测 |

**任何一层不过，就不算交付。** 预算层过而能力层不过，等于"能跑但没用"；能力层过而预算层不过，等于"好用但跑不起来"。

### 1.1 预算层门槛（已可执行）

```bash
python tools/eval_gate.py configs/p1_target.json
```

| 检查 | 门槛 | 当前 |
|---|---|---|
| VRAM 占用 | ≤ 7.0 GiB | 6.45 ✅ |
| VRAM 余量 | ≥ 0.45 GiB | 0.55 ✅ |
| 内存占用 | ≤ 12.0 GiB | 0.35 ✅ |
| 解码上限 | ≥ 30 tok/s | 51.1 ✅ |

退出码：`0` = 全过，`1` = 余量不足，`2` = 超包线，`3` = 配置不可读。

## 2. 能力层：测什么

### 2.1 四个维度

| 维度 | 数据集 | 样本量 | 为什么选它 |
|---|---|---:|---|
| 知识 | MMLU 子集 | 2000 | 覆盖 57 学科，压缩最容易伤"长尾知识" |
| 推理 | GSM8K + BBH 子集 | 1319 + 500 | 数学与多步推理，剪枝最容易伤"链条完整性" |
| 代码 | HumanEval + MBPP | 164 + 427 | 结构化输出，量化最容易伤"语法精确性" |
| 中文 | C-Eval 子集 + 长文摘要 | 1000 + 200 | 词表裁剪最直接的影响面 |

### 2.2 为什么不用单一 benchmark

单一 benchmark 会被优化（无论有意无意）。四个维度覆盖不同的损伤模式：

- **知识** → 参数容量（FFN 宽度）
- **推理** → 层数（深度）
- **代码** → 量化精度（数值噪声）
- **中文** → 词表（token 覆盖）

如果只有一维掉分，能定位到具体是哪个杠杆出了问题。这比一个总分有用得多。

### 2.3 评测执行规范

- **温度 0**，`do_sample=False`，贪心解码
- **统一 prompt 模板**（不针对模型调优，避免"prompt 补偿"）
- **few-shot 数固定**（MMLU 5-shot，GSM8K 8-shot CoT，HumanEval 0-shot，C-Eval 5-shot）
- **每个数据集跑完整，不抽样**（抽样会引入 ±2 分的噪声，掩盖真实差异）
- **报告均值与 95% 置信区间**（用 bootstrap，1000 次重采样）

**排除项**：不跑需要联网的评测，不跑需要人工评分的评测（主观性无法复现）。

## 3. 能力层：和谁比

### 3.1 三个基线，缺一不可

| 基线 | 配置 | 用途 | 怎么跑 |
|---|---|---|---|
| **原版 27B** | 4.5 bpw + KV16 + 8k | 上限参考，衡量压缩损失 | 需要足够的显存；若跑不动，用 CPU offload 慢跑（只要分数不要速度） |
| **P2** | 9.3B / 3.4bpw / 32k | 同硬件"直接换小模型"的对照 | 参考机可跑（7.08 GiB，溢出 0.08） |
| **外部 7-9B** | 同级开源模型 4.0 bpw | 行业对照，防止自嗨 | 参考机可跑 |

### 3.2 判定规则

**P1 必须同时满足**：

1. 相对原版 27B，四类平均掉点 **≤ 6 分**
2. 相对 P2，四类平均 **≥ +3 分**（否则压缩不如直接换小模型）
3. 相对外部 7-9B，四类平均 **≥ +2 分**（否则项目没有存在理由）

### 3.3 证伪条件（写死，不允许事后调整）

| 条件 | 判定 | 动作 |
|---|---|---|
| P1 相对原版掉 > 15 分 | 剪枝过激 | 回退到 28 层重做，接受显存余量降到 0.15 |
| P1 相对 P2 低 > 3 分 | 压缩路线不划算 | **放弃 P1，转做 P2** |
| P1 相对外部 7-9B 低 | 项目无意义 | **终止项目**，公开结论 |
| 真实 tok/s < 预测的 50% | 模型有系统性错误 | 重标定常数，重写 `docs/BENCHMARKS.md` |

**"证伪即终止"是项目诚实性的核心。** 如果一个压缩方案跑不过同硬件的小模型，它就不该存在。

## 4. 体验层：测什么

### 4.1 首 token 延迟（TTFT）

预算模型**完全没有算 prefill**（它假设 decode 受带宽限制，prefill 受算力限制，两者不同）。所以 TTFT 必须实测。

| 输入长度 | 目标 TTFT | 测法 |
|---|---:|---|
| 512 token | ≤ 1.5 s | 跑 20 次取中位数 |
| 2048 token | ≤ 6 s | 同上 |
| 8192 token | ≤ 25 s | 同上，跑 5 次 |

**为什么 8k 目标给到 25 秒**：8 GiB 卡上 8k prefill 是算力受限的硬活。这个数字是"能忍"的上限，不是"好"的标准。

### 4.2 长文稳定性

跑 100 轮 8k 上下文对话，记录：

- 显存峰值是否单调增长（增长 = 泄漏）
- 输出是否在第 N 轮后开始退化（退化 = KV 精度不足或位置编码问题）
- 是否出现 OOM

**判据**：100 轮内显存增长 ≤ 50 MiB，无 OOM，无退化。

### 4.3 交互一致性

同一 prompt 跑 5 次（温度 0），输出必须完全一致。不一致说明有非确定性来源（浮点累加顺序、并发调度），需要定位。

## 6. 反作弊条款

这类项目最容易出的问题是"优化了评测而不是模型"。以下行为明确禁止：

| 禁止 | 原因 |
|---|---|
| 针对 benchmark 调 prompt 模板 | 测的是 prompt 工程，不是模型 |
| 在评测集上做 QAD 蒸馏 | 数据泄漏 |
| 报告最好的那次结果 | 必须报均值与 CI |
| 用抽样代替完整跑 | 抽样噪声掩盖真实差异 |
| 混用不同量化版本的对照 | 必须同精度对照 |
| 只报告通过的项目 | 未测项写 `—`，失败项照实写 |

**发现任一条，该里程碑作废重做。**
