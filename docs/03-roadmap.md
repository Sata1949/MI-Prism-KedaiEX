### 1.1 层重要性排序

**输入**：27B 权重、512 条校准样本（中 40% / 英 40% / 代码 20%）

**三项指标**（每层算一次，在 8k 上下文、batch 1 下）：

| 指标 | 定义 | 含义 | 权重 |
|---|---|---|---:|
| 残差余弦 | `cos(h_in, h_out)` | 接近 1 = 该层近似恒等 | 0.5 |
| 注意力熵 | `-Σ p log p` 平均 | 低 = 退化为局部操作 | 0.3 |
| FFN 稀疏度 | `|act| < ε` 占比 | 高 = FFN 冗余 | 0.2 |

**打分**：
```
score_l = 0.5 × (1 - cos_l) + 0.3 × (1 - H_l/H_max) + 0.2 × (1 - sparse_l)
```

分数低 = 可删。

**硬约束**：
- 首层、末层不可删
- 至少保留 4 个全局注意力层（`global_every=6` 下 26 层里有 4-5 个）
- 相邻层不连续删两层以上（避免语义断层）

**产物**：`{"kept": [0, 2, 5, ...], "dropped": [...], "scores": [...]}`

**已验证的部分**：预算模型已确认 26 层在 7.0 GiB 内（6.45 GiB）。层选得好不好，只能等实测。

### 1.2 层剪枝 + Norm 校准

删层后相邻层的输入分布会偏移。校准方法（仍然是保权重变换）：

对每对相邻保留层 (a, b)，原模型中间被删掉的层整体近似一个恒等映射，但实际不是。用最小二乘拟合一个对角缩放：

```
min_γ  || γ ⊙ LN(h_a) - h_b ||²
```

只有 2×hidden = 10752 个参数，在 512 样本上闭式求解。

**验收**：校准集困惑度增幅 ≤ 8%。超过 8% 说明层选错了，回到 1.1 调整权重。

### 1.3 FFN SVD 收窄

21504 → 18432（保留 85.7%）。方法见 `docs/01-introduction.md` §5.3。

**验收**：每层 FFN 输出与原始输出的余弦相似度 ≥ 0.98（在校准集上平均）。低于 0.98 的层单独保留原宽度（混合宽度是允许的，会增加总参数，需要重新跑门禁）。

### 1.4 词表裁剪

262144 → 131072。低频 token 合并而非丢弃。

**验收**：校准集重新 tokenize 后，序列总长度增长 ≤ 3%。超过说明合并策略太激进（合并后的 token 太"泛"，导致分词碎片化）。

### 1.5 量化

4.0 bpw 主体 + 6.0 bpw 嵌入。**必须用带校准的量化方法**（GPTQ/AWQ 类），不能用直接 round-to-nearest。

**验收**：困惑度增幅 ≤ 3%。这个阈值比 1.2 的 8% 严，因为量化损失是可以通过 QAD 部分回收的，而剪枝损失不可逆。

### 1.6 QAD 回填

**这一步需要真训练，是整个阶段一的最大不确定性。**

- 教师：原 27B（≥ 4.5 bpw）
- 学生：1.5 的输出（带伪量化节点）
- 损失：`KL(teacher || student) + 0.1 × CE(student, labels)`
- 数据：~200M token，与校准集同分布但 disjoint
- 超参：lr 1e-5（cosine），batch 8 × 8k seq，约 30k 步

**验收**：四类核心任务（见 `docs/04-eval-protocol.md`）平均掉点 ≤ 6 分。

**风险预案**：如果 30k 步后仍掉点 > 10 分，按顺序尝试：
1. 只解冻 LayerNorm 与 FFN down 投影（最小干预）
2. 增加数据到 500M token
3. 放弃 26 层，改 28 层（显存回到 6.85，余量 0.15 —— 需要同时把上下文降到 4k）

### 1.7 端到端实测

把预算模型的预测换成真实数字：

- 真实 prefill 速度（模型完全没算这个，因为它假设 decode 受带宽限制）
- 真实 decode 速度 vs 预测 51 tok/s
- 真实显存峰值 vs 预测 6.45 GiB
- 长文稳定性（8k 跑满 100 轮）

**偏差 > 30% 就要重新标定常数**，并把偏差原因写进 `docs/BENCHMARKS.md`。

### 阶段一退出条件

三条同时满足：

1. `tools/eval_gate.py configs/p1_target.json` 返回 0
2. 真实 decode ≥ 30 tok/s（实测，非预测）
3. 四类任务平均掉点 ≤ 6 分

不满足则不进阶段二。

### 2.1 → 2.2 的判据

`docs/01-introduction.md` §6.3 提出"相邻层注意力高度相似则可共享"。这个假设需要数据支撑：

- 若相邻层 Q/K/V 的余弦相似度中位数 > 0.95 → 共享
- 若 < 0.85 → 放弃这条路线，转向 2.3

**这是一条可证伪的假设，不是既定方案。**

### 2.3 结构化稀疏的现实性

RTX 3070 Ti 是 Ampere（compute cap 8.6），支持 2:4 sparse tensor core。但：

- 需要 kernel 支持（cuSPARSELt 或自写）
- 需要训练时施加稀疏约束（否则直接剪到 2:4 会掉很多）
- **本机没有 CUDA toolkit**（`nvcc` 不可用），无法编译自定义 kernel

**阶段二的技术前提不成立。** 这是为什么阶段二标"未进行"而不是"计划中"。

### 2.4 注意力路由的收益测算

**这条已在预算模型上验证过，结论是：收益极小，优先级下调。**

| `global_every` | 全局层数 | `kv_gib`（分配） | `kv_decode_gib`（读） |
|---:|---:|---:|---:|
| 6（当前） | 4 | 0.810 | 0.210 |
| 10 | 2 | 0.810 | 0.160 |
| 26（全局部） | 0 | 0.810 | 0.130 |

**分配量一点没省**：KV 必须为每层预留全量空间，因为训练/推理时任何层都可能被选为全局层。只有解码读取量下降 0.05 GiB，相对 5.48 GiB 的总读取，提速上限 0.9%。

在 8k 上下文下这条改动**不值得做**。只有在 32k 上下文（KV 读取占主导）时才重新评估。

**这条要写进决策记录。** 见 `notes/decisions/0002-attention-routing-low-value.md`。

## 阶段三：Dense 转 MoE + 原生 27B 支持（探索中）

**目标**：27B 参数量级全部保留，但每 token 只激活一部分，从而在 8 GiB 卡上跑起来。

**为什么这是唯一的"真 27B"路线**：Dense 模型每个 token 都要过全部参数，所以 27B Dense 在 7 GiB 显存上不存在解（§3.1 已证明）。MoE 让参数量与计算量解耦，这是唯一的出路。

|---|---|---|---|---|
| 3.0 | 预算模型 | `p3()` + 拓扑扫描 | 已算通（4.82 GiB / 6.54 GiB / 9.4 tok/s） | ✅ 完成 |
| 3.1 | 工具链 | C 编译器 + CUDA | `nvcc --version` 可用 | **阻塞** |
| 3.2 | 专家拆分 | 从 Dense FFN 切分 | 专家间余弦相似度 < 0.9（避免同质化） | 未开始 |
| 3.3 | 路由预热 | 差异化初始化 + 熵正则 | 路由熵 > 0.5 × log(E) | 未开始 |

### 3.1 工具链阻塞（当前最硬的问题）

实测：

```
$ which nvcc gcc cl clang
(全部为空)
$ ls "/c/Program Files/NVIDIA GPU Computing Toolkit/CUDA"
(目录不存在)
```

三条解决路径：

| 路径 | 成本 | 风险 |
|---|---|---|
| 装 CUDA Toolkit | 3 GB 下载，磁盘只剩 15.5 GiB | 磁盘紧张但可行 |
| 用 MSVC Build Tools | 2 GB，无 CUDA | 能写 CPU kernel，不能写 GPU kernel |
| 用 PyTorch 的 JIT（`torch.utils.cpp_extension`） | 需要 torch（未安装，约 2.5 GB） | 自动带 CUDA 编译链 |

**推荐第三条**：装 `torch` 一次解决"没有 CUDA 编译器"和"没有张量库"两个问题。但要先清理磁盘（15.5 GiB 剩余）。

### 3.2 专家拆分的核心难题

从 Dense FFN（21504 宽）切成 12 个专家（每个 4096 宽，2 个激活）：直接按通道切分会得到 12 个"部分功能"的专家，它们只在特定输入上有效，但路由不知道哪个有效 —— 会退化。

正确做法：

1. **按 FFN 神经元的激活模式聚类**（在校准集上记录每个神经元对哪些 token 激活）
2. 聚类成 12 组，每组 4096 个神经元
3. 这样切出来的专家各自"擅长"不同输入类型，路由有信号可学
4. 差异化初始化：每组的 down 投影乘不同的缩放因子

**验收**：专家间的输出余弦相似度 < 0.9。高于 0.9 说明切分没起到分化作用。

### 3.3 路由预热

新增 router（hidden → 12），初始随机。预热目标：

- 负载均衡：每个专家被选中的频率在 `1/12 ± 30%` 内
- 路由熵：`> 0.5 × log(12)`（说明路由不是在瞎选，也不是退化到只选 1-2 个）

损失项：`aux_loss = 0.01 × CV(load)²`（CV = 变异系数）

### 3.4 CPU 反量化 kernel（最关键的工程）

背景：专家在内存里是 2.2 bit 压缩的。送入 GPU 前要在 CPU 上解包成 fp16。

实测瓶颈：Python/NumPy 的 int8 → fp32 路径只有 **0.8 GB/s**（见 `docs/BENCHMARKS.md`）。需要 15+ GB/s。**差 19 倍，必须写 C。**

关键点：

- 8 线程（实测单线程 6.0 GB/s，8 线程 19.3 GB/s）
- 用 `_mm256_cvtepi8_epi32` + `_mm256_cvtepi32_ps`（AVX2）
- 或者用 `_mm256_maddubs_epi16` 做 int8 点积
- Ryzen 7 6800H 支持 AVX2 与 AVX-512（Zen 3+ 是 AVX2，无 AVX-512）

**这里有个必须验证的假设**：2.2 bit 的压缩格式是什么？如果是每 8 个权重共享一个 scale（类似 GGML 的 Q2_K），反量化就是查表 + 乘法，能做到接近内存带宽。如果是更复杂的格式，会慢很多。

### 3.5 异步预取

设计见 `docs/01-introduction.md` §7.3。

关键指标：隐藏率 = `1 - (实际暴露的读取时间 / 总读取时间)`。目标 ≥ 50%（对应 ≥ 20 tok/s）。

**已知的硬限制**：PCIe Gen4 x8 的 11 GB/s 是共享的。如果同时做"读专家"和"写 KV"，会抢带宽。KV 在显存里，理论上不抢，但 `cudaMemcpyAsync` 与 kernel 执行会争用 PCIe 控制器。

### 阶段三退出条件

1. 3.6 达到 ≥ 20 tok/s → 成功
2. 3.4 的吞吐 < 10 GB/s → kernel 路线需要重设计
3. 3.2 的专家相似度 > 0.95 → 拆分失败，需换方法（如蒸馏出专家）

### 关键工程结论：两个阶段的优化方向是相反的

带宽敏感性实测（`notes/decisions/0004`）：

| 配置 | `bw_vram_gbps` 280→400 | `bw_host_gbps` 17→68 |
|---|---|---|
| P1（全常驻） | 51.1 → 73.0（**+43%**） | 51.1 → 51.1（**0%**） |
| P3（专家在内存） | 9.4 → 9.6（**+2%**） | 9.4 → 30.0（**+219%**） |

所以：

- **阶段一优化 GPU 侧**：4-bit GEMV kernel、CUDA graph、KV 布局。不要碰 CPU 侧。
- **阶段三优化 CPU 侧**：AVX2 反量化、双缓冲预取、路由预测。不要优化 GPU kernel（收益 < 2%）。

这条结论直接决定了两个阶段的人力分配，且两者不可复用。

## 时间与优先级

不做时间承诺（这类项目的估算误差通常是 3-5 倍）。只定优先级：

1. **P0**：阶段一 1.1 - 1.5（纯工程，无训练，确定性高）
2. **P0**：阶段一 1.6（训练，最大不确定性）
3. **P1**：阶段三 3.1 - 3.4（MoE 的工程基础）
4. **P2**：阶段二全部（技术前提不成立）
5. **P3**：阶段三 3.5 - 3.6（依赖 3.4）

**阶段二被降到 P2 的理由**：CUDA 工具链缺失，2:4 稀疏无法实现。在解决工具链之前，阶段二的所有里程碑都是纸面设计。
