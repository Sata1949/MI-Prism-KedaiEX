# 架构勘误：v1 的参考架构是错的

> 日期：2026-11-17
> 触发：把仓库迁到 D 盘时，顺手读了本机已有的真实 GGUF 头部。
> 结论：**v1 的 `configs/ref_27b.json` 里每一个字段都与真实模型不符。**
> 影响：不影响"27B 放不进 7 GiB"这个主结论，但让所有具体方案数字失效。

---

## 1. 怎么发现的

D 盘上有 `moss-image/moss27b/models/ms_dl/Qwen3.8-27B-UD-IQ3_S.gguf`（11.21 GiB）。GGUF v3 的头部是不加密的 KV 表 + 张量表，可以直接解析，不需要加载权重：

```python
# 读取 GGUF header（见 tools/gguf_peek.py）
magic, ver, n_tensors, n_kv = ...
# 然后逐个读 key/value 与 tensor descriptors
```

866 个张量、50 个 KV 对，全部拿到。这部分**没有猜测成分**，是文件里的字节。

---

## 2. 对照表：v1 假设 vs 实测

| 字段 | v1 假设 | **实测** | 影响 |
|---|---:|---:|---|
| hidden | 5376 | **5120** | 权重规模、SSM 维度 |
| layers | 62 | **65** | 层剪枝的全部方案 |
| 注意力结构 | 62 层纯注意力 | **17 全注意力 + 48 线性注意力** | **质变，见 §3** |
| heads | 32 | **24** | 注意力参数 |
| kv_heads | 16 (GQA 2:1) | **4 (MQA 6:1)** | **KV 缓存小 8 倍** |
| head_dim | 128 | **256** | 单 token KV 字节 |
| FFN | 21504 | **17408** | 最大的一块权重 |
| vocab | 262144 | **248320** | 嵌入规模 |
| tie_embed | true | **false** | **多出 1.27B 输出层参数** |
| 局部/全局 | 6:1 滑窗 | **4:1（每 4 层 1 个全注意力）** | 长上下文成本 |
| 上下文 | 8192（项目假设） | **262144（原生）** | 见 §4 |
| MTP | 无 | **有 1 层 nextn** | 额外的投机解码可能 |

**v1 一个字段都没对。** 这不是"近似不精确"，是"描述的是另一个模型"。

---

## 3. 最关键的差异：48 层线性注意力

真实模型是 Qwen3-Next 风格的混合架构：

```
65 层 = 17 层全注意力（每 4 层一个）
     + 48 层线性注意力（gated DeltaNet 风格 SSM）
每层都有 17408 宽的 FFN
```

线性注意力的状态是**固定大小**，不随上下文增长：

```
每层状态 ≈ inner_size × state_size = 6144 × 128 = 786,432 元素
48 层合计 @fp16 = 72 MiB   ← 常数
```

这意味着两件事：

**第一，长上下文极便宜。** 只有 17 层产生 KV：

| 上下文 | KV16 | KV8 |
|---:|---:|---:|
| 8k | 0.53 GiB | 0.27 GiB |
| 32k | 2.12 GiB | **1.06 GiB** |
| 131k | 8.50 GiB | 4.25 GiB |
| 262k | 17.00 GiB | 8.50 GiB |

对比 v1 假设的 62 层 GQA 16 头：32k 需要 3.25 GiB。**真实模型只有 1.06 GiB，便宜 3 倍。**

**第二，层剪枝的语义完全变了。** v1 的 `docs/03-roadmap.md` §1.1 说"用三项指标选 26 层"。但真实模型里 48 层线性注意力和 17 层全注意力**功能不同**，不能用一个统一的"重要性分数"去排序 —— 删掉一个全注意力层（唯一能做精确检索的层）和删掉一个线性注意力层（做状态累积）后果完全不同。

**v1 的层重要性排序方案不可直接沿用。**

---

## 4. 长上下文：v1 严重低估了真实能力

v1 的 P1 目标写"8k 上下文"，因为 62 层 × GQA16 的 KV 太贵。

真实模型在 8 GB 卡上（假设权重压到 3.0 bpw）：

| 配置 | 权重 | KV(32k) | 总显存 | 可行 |
|---|---:|---:|---:|---|
| 全 65 层 @3.0bpw | 10.42 | 1.06 | 11.50 | ✗ 超 4.50 |
| 全 65 层 @2.0bpw | 7.54 | 1.06 | 8.62 | ✗ 超 1.62 |

**即使 2.0 bpw + 32k 也放不进。** 因为权重本身太大（未共享词表 1.78 GiB 是固定负担）。

所以真实结论是：

> **真实模型的长上下文能力很强，但它的权重根本装不进 7 GiB。这两件事不矛盾 —— 便宜的是 KV，不是权重。**

---

## 5. 对现有方案的影响

### 5.1 不受影响的结论

- "27B 放不进 7 GiB" —— **成立，且更成立**。本机实测 IQ3_S 文件就是 11.21 GiB。
- "必须剪枝" —— 成立。
- "优化方向 P1 在 GPU 侧、P3 在 CPU 侧" —— 结论逻辑仍成立，但具体常数需重算。

### 5.2 失效的数字

| 位置 | v1 数字 | 状态 |
|---|---|---|
| `configs/ref_27b.json` 全部字段 | 见 §2 | **全部作废**，已用 `qwen38_27b_real.json` 替代 |
| README / docs 的 19.02 GiB 基线 | 基于错误架构 | 需重算 |
| P1 = 26L / FFN 18432 / 128k / 4.0bpw | 基于错误架构 | 需重算 |
| P1-low = 26L / FFN 14336 / 3.5bpw | 同上 | 需重算 |
| 层重要性排序方案（26 层） | 不分全/线性注意力 | **方法需重设计** |
| 62 → 26 的"剪层占 80% 节省" | 基于错误架构 | 需重算 |

### 5.3 重算后的初步方案（待验证）

用真实结构（17 全 + 48 线性，FFN 17408，vocab 248320 未共享）：

| 方案 | 参数 | 权重 | KV(8k) | 总显存 | 余量 |
|---|---:|---:|---:|---:|---:|
| 65L 全量 @3.0bpw | 24.73B | 10.42 | 0.27 | 11.50 | −4.50 |
| 48L(17f/31l) @3.0bpw | 18.21B | 8.14 | 0.27 | 9.20 | −2.20 |
| 40L(17f/23l) @4.0bpw | 15.15B | 8.83 | 0.27 | 9.88 | −2.88 |
| 32L(12f/20l) @4.0bpw | 12.14B | 7.43 | 0.19 | 8.39 | −1.39 |
| 32L(12f/20l) @4.0bpw, vocab 50% | 12.14B | 6.54 | 0.19 | 8.07 | −1.07 |
| 28L(8f/20l) @4.0bpw, ffn75+vocab50 | 10.05B | 4.75 | 0.12 | 5.85 | **+1.15** |

**初步结论：要进 7 GiB，必须同时砍层、砍 FFN、砍词表三者都动，比 v1 更激进。**

## 6. 这次错误的教训

v1 的 `ref_27b.json` 是我凭印象写的"典型 27B 参数"，然后整套文档都在这个虚构架构上做精确计算。精度很高，对象是错的。

**这和 §10.7 那次审计事故是同一类错误的两个变体：**

| 事故 | 验证对象 | 缺陷 |
|---|---|---|
| `audit_docs.py` v1 | 文档数字 | 审计与被审计共享输入，等于没审 |
| `ref_27b.json` v1 | 模型架构 | 从未与真实制品核对，等于虚构 |

**共同的修正方式：让断言绑定到外部事实，而不是绑定到我自己的记忆。**

- 文档数字 → 绑定到模型输出（`audit_bindings.py`）
- 模型架构 → 绑定到 GGUF 头部（`configs/qwen38_27b_real.json` 的 `provenance` 段 + `tools/gguf_peek.py`）

已加入规则：**任何"参考架构"必须标注来源文件与提取方式，无法标注的不许出现在文档里。**
