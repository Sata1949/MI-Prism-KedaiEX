# 风险表

> 按"影响 × 可能性"排序。每条包含：触发条件、后果、缓解方式、当前状态。
> 状态含义：**已确认** = 已实测到；**已缓解** = 有对策且验证过；**未验证** = 有对策但没跑过；**开放** = 无对策。

---

## 阻断级（会让项目停摆）

### R1 · 磁盘不足，装不下 27B 权重

| 项 | 内容 |
|---|---|
| 触发 | 需要下载 27B 权重做剪枝与 QAD |
| 实测 | C 盘剩余 **15.5 GiB**（`df -h /c` → 199G total / 184G used / 16G avail） |
| 后果 | 27B 在 4.5 bpw 下是 14.39 GiB。**加上中间产物（剪枝副本、QAD checkpoint），15.5 GiB 完全不够** |
| 缓解 | ① 清理 C 盘；② 外接盘或 D 盘；③ 只用 4.5 bpw 的单份权重，边剪边删中间产物 |
| 状态 | **已确认，未解决** |
| 备注 | 这个风险比显存风险更早触发。显存问题在预算模型里已经解决，磁盘问题还没有 |

### R2 · 没有 C 编译器与 CUDA 工具链

| 项 | 内容 |
|---|---|
| 触发 | 阶段二（2:4 稀疏 kernel）与阶段三（CPU 反量化 kernel、CUDA stream 预取） |
| 实测 | `which nvcc gcc cl clang` → 全部为空；`/c/Program Files/NVIDIA GPU Computing Toolkit/CUDA` 不存在 |
| 后果 | 阶段二整体阻塞；阶段三的 3.4 / 3.5 无法实现 |
| 缓解 | 三条路径：① 装 CUDA Toolkit（3 GB）；② 装 MSVC Build Tools（2 GB）；③ 装 PyTorch（2.5 GB，自带 JIT 编译链 + CUDA）。**推荐 ③**，一次解决编译器 + 张量库 |
| 状态 | **已确认，未解决**（与 R1 冲突：磁盘不够） |

### R3 · QAD 回填效果不足

| 项 | 内容 |
|---|---|
| 触发 | 阶段一 1.6，剪枝后掉点 8-12 分需要回填 |
| 依据 | 剪枝 58% 参数 + FFN 收窄 14% + 词表砍半，这个组合的掉点在同类工作中通常是两位数 |
| 后果 | 阶段一无法达到"掉点 ≤ 6 分"的退出条件 |
| 缓解 | ① 分阶段解冻（先只训 LayerNorm）；② 数据加到 500M token；③ 回退到 28 层 |
| 状态 | **未验证**（需要权重与训练资源） |

## 高危（会让结论失效）

### R4 · 预算模型的速度预测偏差过大

| 项 | 内容 |
|---|---|
| 触发 | 端到端实测（阶段一 1.7） |
| 具体风险 | 51.1 tok/s 是**带宽受限假设下的上限**。真实 decode 还受 kernel 效率、Python 开销、同步开销影响，实际可能只有 30-40 tok/s |
| 后果 | 若低于 30 tok/s，阶段一的"能用来写代码"目标落空 |
| 缓解 | ① 目标定 30 而不是 51；② 用 llama.cpp 类的高效 runtime 而非 PyTorch 逐层循环；③ 端到端实测后重标定 `BW_VRAM_GBPS` |
| 状态 | **未验证**，偏差会写进 `docs/BENCHMARKS.md` |

### R5 · 层重要性排序选错层

| 项 | 内容 |
|---|---|
| 触发 | 阶段一 1.1，用三项指标打分 |
| 具体风险 | 62 → 26 是 58% 的剪枝率，这个幅度下"选哪层"的影响可能大于"选多少层"。指标权重（0.5/0.3/0.2）是拍的 |
| 后果 | 掉点远超预期，且不知道是"剪太多"还是"选错层" |
| 缓解 | ① 先做敏感性分析：删单层看掉点，找出真正的关键层；② 保留至少 2 套候选方案对照；③ 用残差余弦作为主指标（它有明确的理论依据：接近 1 的层是恒等映射） |
| 状态 | **未验证** |

### R6 · FFN SVD 收窄破坏激活分布

| 项 | 内容 |
|---|---|
| 触发 | 阶段一 1.3，21504 → 18432 |
| 具体风险 | SVD 保持的是线性映射的 L2 误差，但 FFN 后面接的是 SwiGLU 非线性。线性层面相似度高，不代表激活后相似度高 |
| 后果 | 困惑度增幅超 8%，需要回退部分层到原宽度 |
| 缓解 | ① 验收指标用"FFN 输出余弦"而不是"权重矩阵误差"；② 逐层验收，不达标就保留原宽（混合宽度允许）；③ 在激活之后加一次重标定 |
| 状态 | **未验证** |

### R7 · 词表合并导致分词碎片化

| 项 | 内容 |
|---|---|
| 触发 | 阶段一 1.4，262144 → 131072 |
| 具体风险 | 低频 token 合并到最近邻。若最近邻选得不好，原本 1 个 token 的词会被拆成 3-4 个 |
| 后果 | 序列变长，速度下降，且**显存收益被抵消**（更长的序列 = 更多 KV） |
| 缓解 | ① 验收"序列长度增长 ≤ 3%"；② 合并时优先合并语义相近的 token（不只是嵌入最近邻）；③ 保留中文与代码的高频 token 不动 |
| 状态 | **未验证** |

## 中危（有对策）

### R8 · 显存碎片化导致假性 OOM

| 项 | 内容 |
|---|---|
| 触发 | 多次分配释放（尤其 KV 动态增长） |
| 后果 | 明明有余量却 OOM |
| 缓解 | ① 启动时预分配 KV 池（按 max_ctx）；② 禁用 PyTorch 的 `expandable_segments` 之外的动态增长；③ 保留 0.55 GiB 余量 |
| 状态 | **已缓解**（余量设计与预分配策略） |

### R9 · KV4 在长上下文崩坏

| 项 | 内容 |
|---|---|
| 触发 | 用 KV4 跑 16k+ 上下文 |
| 后果 | 长文注意力精度崩坏，表现为"忘记开头" |
| 缓解 | ① 8k 内用 KV8；② 16k 必须 KV8；③ 32k 不用（P1 架构不支持）；④ 若必须长文，改用 KV8 + 24 层 |
| 状态 | **已缓解**（策略层面），**未实测** |

### R10 · 笔记本降频导致速度不稳

| 项 | 内容 |
|---|---|
| 触发 | 长时推理，GPU 温度墙 |
| 实测 | 探针的 `--quick` 模式第一次跑出 copy 11 GB/s（正常 22），确认存在降频现象 |
| 后果 | 长跑速度比短测低 20-50% |
| 缓解 | ① 所有基准测试前预热 0.7 s（已实现）；② 报告"稳定态"速度而非"峰值"；③ 记录 GPU 温度 |
| 状态 | **已缓解**（预热已实现并验证：预热后 18.8-20.5 GB/s，未预热 7.6-8.0） |

### R11 · PCIe 实际是 x8 而非 x16

| 项 | 内容 |
|---|---|
| 实测 | `nvidia-smi` → `Link Width Max: 16x`，`Current: 8x` |
| 后果 | 溢出配置的 PCIe 成本比预期高一倍 |
| 缓解 | 预算模型已用 11 GB/s（x8 的实测有效值），不是 x16 的 22 GB/s |
| 状态 | **已缓解**（常数已按实测标定） |

### R12 · 内存单条，无双通道

| 项 | 内容 |
|---|---|
| 实测 | `Win32_PhysicalMemory` 只有 1 条 16 GiB Micron（`ConfiguredClockSpeed 4800`） |
| 推算 | DDR5-4800 单通道理论 **38.4 GB/s**（4800 MT/s × 8 B）；实测 19.3 GB/s = **50% 效率**（正常水平）。双通道理论 76.8 GB/s，同效率约 38 GB/s |
| 后果 | P3 的 host 流式读取路线受重创：9.4 tok/s 而非双通道下的约 19 |
| 缓解 | 无软件手段。但**加一条 16 GiB 是最便宜的提速手段**（见文末） |
| 状态 | **已确认，无法用软件缓解** |
| 备注 | 注意 50% 效率不高不低，说明实测值可信；不是"带宽没跑满"，是单通道的物理上限 |

## 低危（记录在案）

### R13 · Python 反量化吞吐极低

| 项 | 内容 |
|---|---|
| 实测 | int8 → fp32 的 NumPy 路径 **0.6-0.8 GB/s**，比内存带宽（19.3）低 24 倍 |
| 后果 | P3 若用 Python 做反量化，速度会崩到 0.4 tok/s |
| 缓解 | 必须写 C/C++ 扩展（AVX2） |
| 状态 | **已确认**，见 R2 |

### R14 · 探针测量的抖动

| 项 | 内容 |
|---|---|
| 实测 | 同一机器，`mem read` 在 18.8-20.5 GB/s 间波动（3 次），`gemv` 在 10.46-11.19 GFLOPS 间波动 |
| 后果 | 单次测量不可信 |
| 缓解 | ① 取 3 次最优；② 预热；③ 报告区间而非单点 |
| 状态 | **已缓解** |

### R15 · 混合注意力下 KV 分配不可省

| 项 | 内容 |
|---|---|
| 实测 | `global_every` 从 6 改到 26，`kv_gib` 保持 0.810 不变，只有 `kv_decode_gib` 从 0.210 降到 0.130 |
| 后果 | 任何"减少全局层来省显存"的方案都无效 |
| 缓解 | 已从文档中删除该假设，改为只宣称速度收益（且收益 < 1%） |
| 状态 | **已确认并修正**，见 `notes/decisions/0002` |

## 最便宜的改进

按"投入产出比"排序：

1. **加一条 16 GiB 内存条**（约 ¥200-400）：内存带宽翻倍，P3 速度从 9.4 → 约 18 tok/s，同时解除 R12
2. **清理 C 盘 30+ GiB**：解除 R1，让阶段一可以开始
3. **装 PyTorch**：解除 R2 的编译器部分（磁盘允许的前提下）
4. **改 28 层**：如果 R3/R5 导致掉点过大，这是备选方案（代价：余量降到 0.15 GiB）

前两项是纯硬件/环境操作，不涉及任何模型工作，应该最先做。
